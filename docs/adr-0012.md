# ADR-0012: Begrenzte Anpassung der CAN-Linkverwaltung für vcan

Status: experimentell, 20.10.2026. Kein vollständiger CAN-/DALI-Emulator.

## Problem und Ist

Die genuine FW31-`libcanopen.so.1.4` ruft dynamisch die Linkverwaltung von
`libsocketcan.so.2` auf. Im isolierten Originalruntime-Versuch lehnt Linux
das Setzen von 125000 Bit/s auf `vcan` mit `EOPNOTSUPP` ab. Der Treiber
wiederholt den Anlauf und meldet anschließend einen Initialisierungstimeout.
Das wurde per Syscall-Trace beobachtet. Eine laufende IEC-Anwendung allein
belegt deshalb keine erfolgreiche I/O-Konfiguration.

## Ziel und Entscheidung

Runtime, I/O-Manager, CANopen-Treiber und CAN-Telegrammtransport bleiben
original. Ein eigener, explizit geladener Adapter an der dynamischen
libsocketcan-Grenze behandelt nur drei Operationen für ein vom Kernel per
Netlink als `vcan` bestätigtes Interface namens `can0`:

- `can_set_bitrate(..., 125000)` akzeptiert virtuelle Konfigurationsmetadaten.
- `can_set_restart_ms(..., 2000)` akzeptiert virtuelle Konfigurationsmetadaten.
- `can_get_state` projiziert den tatsächlichen Linkzustand UP/DOWN auf
  `CAN_STATE_ERROR_ACTIVE` / `CAN_STATE_STOPPED`.

Andere Parameter des virtuellen Links werden abgelehnt. Andere Interfaces
gehen an die genuine Bibliothek weiter. Der Interface-Name allein genügt
ausdrücklich nicht zur Auswahl. CANopen-Anfragen, NMT, PDOs, SDOs und
DALI-Antworten werden hier weder erzeugt noch quittiert.

## Alternativen

Unverändertes `vcan` scheiterte am belegten Kernelvertrag. Ein physischer
CAN-Test bleibt separat möglich, ist aber kein Nachweis für Virtualisierung.
Ein Eingriff in Kernel oder Originaltreiber wäre wesentlich umfangreicher.
Eine nachgeschriebene IEC-CANopen-Logik würde die gewünschte Ersatzgrenze
verlassen.

## Risiken und Grenzen

Akzeptierte Bitrate bedeutet keine Simulation der Übertragungsdauer oder
Arbitration. Die Zustandsprojektion bildet administratives UP als virtuelle Näherung ab;
das ist keine allgemeine Gleichsetzung mit einem fehlerfreien physischen
CAN-Controller. Sie modelliert keine Fehlerzähler, Bus-off-
oder Wiederanlaufsemantik. Sie ist keine Behauptung, dass ein realer Bus
fehlerfrei wäre. Dynamische Symbolauflösung und weitere Abhängigkeiten müssen
am konkreten Originalstack geprüft werden. Dieser Adapter allein ist kein
CANopen-Knoten und kein DALI-Modell.

Der Versuch läuft ausschließlich in einer getrennten Netzwerk-Namespace
ohne physisches CAN und ohne Ethernet. Es gibt keine Bridge zum Referenzbus.
Die Rücknahme beendet den eigenen Prozess; Originalbibliotheken bleiben
unverändert.

## Verifikation

Hardwarefreie Tests prüfen die Weitergabe an einen nachfolgenden Provider.
Der separate native Probe prüft in einer privaten vcan-Namespace erlaubte
und abgelehnte Parameter, Linkzustände sowie negative Interfacefälle.
Originalruntime-, Transport- und Teilnehmerabnahme werden getrennt im
[aktuellen CAN-Bericht](can-native-boundary-2026-10-20.md) und der zugehörigen
Evidence dokumentiert. Kein Test dieses ADR behauptet einen DALI-Kontakt.

Versuch M: Originalruntime RUN, 275 CAN-Frames, kein virtueller Teilnehmer.
Native Probe nach technischer Prüfung auf ausschließlich lo/vcan: DOWN/UP
PASS. Der Adapter ersetzt keine SDO-/PDO-/DALI-Antworten.
