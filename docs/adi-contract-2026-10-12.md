Date: 2026-10-12 UTC. The binary contract analysis was static and offline. Its workers accessed no VM, device, or network and loaded no original WAGO component. The integrator separately executed only the own adapter/harness with GNU loader/libc in validated offline roots. This report contains derived interface names and findings, not copied manufacturer headers or raw disassembly. ## Evidence binding and scope

Later evidence on the real controller is recorded separately in [the observation and contract delta](real-controller-observation-2026-10-12.md): existing runtime-owned K-Bus/UIO endpoints, concurrent task classes, and passive cached D-Bus queries. The own sixteen-bit candidate, frame and logical-watchdog rules remain model policy; no deployment or original-consumer acceptance is inferred. [ADR-0003](adr-0003.md) prioritizes the real controller with simulated I/O over a fully virtual runtime.

The backed-up reference `libdal.so.1.0.1` SHA-256 is `c163ac57805409921ce783f9c4f17f52891864be333c3df4945a128d253994f5`. It is byte-identical to the FW30 SDK `libdal.so.1.0.1` artifact bound in the prior ABI manifest. Header scope is WAGO PFC SDK `FW30-V04.08.09`, repository commit `252209115885442bac7359a2ff1cfa4efb3a9c84`, not a claim that the API header itself was compiled for FW31.

The actual backed-up FW31 consumers are distinct builds: `libIoDrvDal.so.1.0.2` SHA-256 `853d3ad6eb1b2477b43502d562a6bbfa854b8029e85989b6166f961167188c7d` and `libIoDrvKbus.so.0.0.1` SHA-256 `543e8b1d2d19352030fe804a7e667ca30c1d9ba80069f2df3158c77c544789b8`. The actual FW31 `libpackbus.so.1.0.1` SHA-256 is `3b7b7ca4fa14e5994552040a7b40b1cfbbf43e0649a4ad9277ece421fd4bc5d6`; the separate pinned FW30 packbus artifact is `00537de62e3c4b19cda3f24f6e6e1308ec03dc8d0c761537690a0e7f5f3cbd47`. Static `ComponentEntry` in `IoDrvDal` obtains `adi_GetApplicationInterface()` and copies `0x88` bytes, consistent with 34 32-bit function pointers. The header probe reports those offsets for the FW30 header under ARM32 hard-float GCC 14.2.0; the FW30 SDK specifies GCC 11.3.1. This confirms table size/order consistency for the supplied evidence, not a FW31 build-toolchain identity.

The compile-only probe now asserts the expected C function-pointer type and four-byte slot offset for all 34 ADI entries against the private, hash-bound FW30 headers. It also records FW30 `tCONFIGURE_DEVICE` and `tKBUS_TERMINAL_INFO_32` layout values without copying either declaration into this repository. This binds the header-side prototypes/layouts to GCC 14.2.0 ARM hard-float for this probe only; it does not establish FW31 header provenance or toolchain identity. The compile completed without linking or execution.

## Behavior, lengths, errors, and lifecycle

The genuine header returns `int32` for status slots and defines `DAL_FAILURE=-1`, `DAL_SUCCESS=0`, `DAL_NOTUSED=1`. Its comments generally describe zero on success and `-1` on failure. For device-specific calls the documented outer result distinguishes invoked (`0`), failed (`-1`), and unsupported (`1`); the device-specific return value is a separate result written through `returnValue`. Those are header-scope statements; do not treat them as complete FW31 behavior for every slot.

Static analysis of the byte-identical provider confirms these narrower behaviors:

- `GetDeviceList` treats capacity as a number of `tDeviceInfo` entries, stores total count through the output pointer, then copies at most capacity entries. Capacity zero causes no list write in that provider. This corrects a capacity-in-bytes use in the historical example; do not repeat that example's call pattern.
- `ReadBytes` and `WriteBytes` reject 32-bit `offset + size` overflow and reject ranges whose end exceeds the configured input/output extent before dispatching to the device implementation. The provider’s generic validation does not define terminal-specific byte semantics.
- `GetDeviceName` requires a nonempty destination buffer on the examined path, copies no more than its size, writes NUL to the final buffer byte, reports the length of the copied string, and returns failure if the resulting copied length is zero.
- `RegisterEventHandler` forwards the handler and user data to the opened device; unregister forwards device and handler. No supported evidence establishes callback thread, reentrancy, callback overlap, post-unregister lifetime, or draining of in-flight callbacks.

In `IoDrvDal`, the static path enumerates with `GetDeviceList` capacity 10, finds a matching device name and calls `OpenDevice`; a returned device id is retained by the original native-driver object. The consumer also calls `Init`, `ScanDevices`, `Exit`, `ApplicationStateChanged`, and all four watchdog entries. The generic `IoDrvDal` process-data callbacks pass task id zero and ignore the return values from their observed start, bit/byte transfer, and end calls. This is consumer behavior, not a statement that a replacement provider should ignore its own errors for the Kbus caller.

In the Kbus consumer, input uses ReadStart and then mapped bit/byte operations before ReadEnd; output uses WriteStart and then mapped bit/byte operations before WriteEnd. Start and data-operation results feed observed error branches. ReadEnd and WriteEnd are called, but their return values are discarded when the prior accumulated operation status is restored; do not infer an end-slot failure response from this binary. The provider comments call start/end the process-image read/write transaction boundary; neither evidence source establishes cross-task atomicity or a global lock guarantee. Main-path Kbus task IDs are zero. The byte wrapper’s length checks are provider-bound; map interpretation and connector lengths are Kbus/CODESYS contracts and remain only partially resolved.

For device diagnosis, Kbus passes its device id, a size/buffer pair and an output bus-state location; callsites include zero-size/NULL-buffer checks and a diagnosis buffer in other paths. One code path requires a successful diagnosis call and expected state before module scanning continues. The consumer’s static state checks are observable, but the full mapping from all Kbus/DAL errors to CODESYS diagnosis states is not established.

`CallDeviceSpecificFunction` is a variadic ABI boundary. The exact FW31 `libpackbus` descriptor table gives terminal-info32 three arguments (`uint32`, pointer, pointer) and signed 32-bit result; `read_table_9` two arguments (`uint8` promoted to `int`, `uint16 *`); `read_conf_reg` three (`uint8` promoted to `int`, `uint8` promoted to `int`, `uint16 *`); `get_uid` two (`uint8` promoted to `int`, output pointer); and `Push` zero arguments. The descriptor table and handler code are from FW31 `libpackbus` SHA-256 `3b7b7ca4fa14e5994552040a7b40b1cfbbf43e0649a4ad9277ece421fd4bc5d6`; no proprietary header or raw disassembly is reproduced here. `read_table_9` returns inner `-1` for terminal 0/out of range, `-2` for null output, otherwise stores the uint16 module id and returns 0 when nonzero or 2 when zero. `read_conf_reg` returns 2 when no rail is present, `-1` for invalid slot, `-3` for null output, `-2` for unsupported terminal/register, and otherwise returns the rail-register helper result. `get_uid` validates slot/output, writes the module identity through the original helper, and returns that helper's result; the virtual model does not fabricate identity. Push's descriptor shape is bound; its handler success/error behavior is not fully analyzed.

The Kbus consumer dispatch sites include direct load/calls at `0x26ac/0x26b8` (terminal-info32), `0x2754/0x2758` (Push), `0x2ba4/0x2bb4` and `0x3084/0x3090` (get_uid), `0x2d64/0x2d6c` (read_conf_reg), `0x3a3c/0x3a48` (terminal-info32), `0x5614/0x5628` and `0x7324/0x7330` (read_table_9), `0x56a4/0x56b0`, `0x56f0/0x56fc`, `0x5730/0x5738`, `0x5770/0x577c` (read_conf_reg), and `0x67ac/0x67b0` (Push). Four further slot-0x70 function pointers loaded at `0x7394`, `0x73b0`, `0x73d0`, and `0x7408` are passed to helper `0x6d24`, which dispatches the supported register/terminal helper operation at `0x6d54`.

The FW31 Kbus `ConfigureDevice` call at `0x3a14` passes a 12-byte object: discriminator 3 at offset 0, runtime-selected 32-bit control value at offset 4, and false at offset 8. The matching FW30 type-III declaration agrees with the actual FW31 consumer branch and 12-byte copy, so this callsite's config layout is statically bound for those binaries. The selected value is runtime-dependent; the own model only accepts TCM control zero and explicitly rejects the unmodeled enable value.

For terminal-info32, Kbus preflight at `0x26b8` supplies a valid temporary record buffer, capacity zero and count pointer, expecting the handler's inner result 2. The normal call at `0x3a48` supplies capacity 4000 bytes, a record buffer and count pointer; outer and inner results are ORed at `0x3a4c–0x3a50`, and nonzero is an error on this path. The FW31 handler writes count, returns 1 for null records/count pointers, returns 2 when capacity is smaller than count×16, copies records for sufficient capacity, and zero-fills excess after copying. The own harness covers cap 31/no write, exact 32, cap 4000/zero tail and canary, null records, and the separate model's 9001/9002 table values. Push's handler result interpretation, active project terminal selection/order, and remaining service/lifecycle reachability remain **OFFEN**. The FW30 SDK `libpackbus.h` hash is `ebde7a6efb590f56f18b6b5e146baa8c6483a1a3ba53f45b07697065ee406379`; its separate FW30 provider binary hash is `00537de62e3c4b19cda3f24f6e6e1308ec03dc8d0c761537690a0e7f5f3cbd47`.

## Smallest replacement cut and current implementability

The smallest **named function-table seam** beneath the preserved WAGO consumers is the provider returned by `adi_GetApplicationInterface()`: retain the original runtime, CODESYS I/O manager, `IoDrvDal`, and `IoDrvKbus`, and substitute only the implementation behind the 34-entry ADI table. Provider identity and header signatures are bound for the actual `libdal` bytes, while Kbus reachability is separately bound to the exact FW31 consumer hash above. This establishes an API boundary, not proof that it is the complete lower hardware cut. The exact Kbus binary also has `DT_NEEDED` dependencies on `libwago_dbus.so` and `libdiagnostic.so` (besides `libIoDrvDal.so.1` and D-Bus/GLib libraries); service-side effects and their relation to the process-data path were not closed by this ADI analysis.


The exact secured `IoDrvDal.cfg` selects DAL name `libpackbus` for `libIoDrvKbus` / `IoDrvKbus_Init`; the CODESYS driver label in that configuration is separately `Kbus`. The observed `IoDrvDal` loader matches `tDeviceInfo.DeviceName` against the DAL name. The adapter model therefore exposes `libpackbus`, with its own opaque device id `1` that the consumer obtains from the list. Neither value claims a physical device identity.

An own in-memory adapter slice is now implemented in [`tools/adi_digital_adapter.c`](../tools/adi_digital_adapter.c), with an own contract harness in [`tools/adi_digital_adapter_test.c`](../tools/adi_digital_adapter_test.c). It uses the genuine private FW30 ADI and packbus headers at compile time and does not copy their declarations. It supports the observed initialization/list/open/configure path, two 16-bit digital channels, cyclic bit/byte transfers, the supported `Push`, `read_table_9`, and terminal-info32 calls, diagnosis state, application state, and watchdog entry points. It rejects unsupported terminal/register UID queries and unknown device-specific names explicitly. Its 2-byte input and output extents and terminal metadata packing are **own model policy**, derived from the installed descriptors' two 16-bit channels and the Kbus binary's 9001/9002 fast path; they are not measured `GetIoSizes` results, active configuration, or physical layout. The model accepts only type-III TCM control zero with the observed false new-process-image flag; it fails closed on unmodeled TCM enablement. The adapter keeps requested outputs distinct from effective outputs and applies its documented fail-closed permit/application/watchdog policy. The read latch and staged write commit are own deterministic frame semantics, not claimed provider or device behavior. A write end requires all 16 output bits to have been supplied during that transaction; any invalid operation or loss of an output gate poisons and aborts the staged frame. Close/reopen clears configuration and output permissions so a fresh lifecycle starts fail-closed.

The adapter and harness pass compile-only checks with ARM hard-float GCC 14.2.0 against those private FW30 headers; the own-code harness executable also links successfully as an ARMHF PIE. No original WAGO DAL, I/O driver, packbus, or runtime code was linked or executed. The executable has SHA-256 `1f612a2a5eb70f151fb83eba0511e51a287147948a13568260b90672e0d5c75c`; adapter, header, and harness source hashes are `7da0d31316648041cd1818291bb209030b1b7d9b8d83d49bb2a368289a0edfff`, `f4a5760093dabf5f358b6ca61b27af51d5e6460f9cd14e0b2abfff8d5ca83086`, and `9cfd3c287883d5730ffadec8bec335890181b22ee5f8edf592c120123a1799d5`, respectively. The source compile and own-code link pass do not qualify original-consumer, runtime, sandbox, device, or hardware acceptance. **PASS, own-model execution:** the root integrator ran the reviewed harness under ARM/QEMU, and separately ran an own harness dynamically loading the own `libdal.so` model. Both exact roots passed isolation controls; the intentionally injected guest file produced the expected failing isolation probe. See [consolidated execution evidence](../evidence/originalstack-block-validation-2026-10-12.json). GNU loader/libc executed; no original WAGO component.

Accordingly, the contract matrix provides enough evidence for this bounded own ADI model, but does not establish a complete safe original-consumer DI/DO slice or prove the smallest complete hardware cut. The original manager remains responsible for its connector/mapping objects; their missing internal layouts are not a blanket prerequisite. The selected native project/tree/mapping binding, remaining opcode/error interpretation, callback/lifecycle semantics, and Kbus D-Bus/diagnostic lower-service closure remain **OFFEN**. The supported next result is an own-model compile/contract qualification; the original-stack M3 path remains **BLOCKED** on those distinct gates. No custom CODESYS manager or connector model is introduced.
