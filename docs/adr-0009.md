# ADR-0009: Native CODESYS integration before physical module fidelity

Status: beschlossen am 19.10.2026. This decision prioritizes integration of virtual, descriptor-pinned modules through the original CODESYS runtime and I/O path. It does not claim physical equivalence or qualify an analog/PWM hardware comparison.

## Problem und Ist

The project has an original-stack digital path and exact local CODESYS descriptions for additional analog and PWM modules. Those descriptions expose process fields and a parameter-10 module-compare value. Existing FW31 consumer analysis also binds Table9 and selected configuration-register predicates. The descriptor and consumer checks are enough to define an explicit virtual compatibility profile, but do not establish physical register defaults, status projection, electrical behavior, or the actual hardware process image.

The prior evidence kept native analog/PWM execution behind open physical-projection and register-semantic gates. The owner now prioritizes making the original CODESYS consumer accept and use virtual profiles; comparison against physical analog/PWM modules is later work. Current physical comparison scope is limited to separately authorized DI8/DO8 work.

## Ziel

Allow a bounded implementation to test selected CODESYS virtual modules against the unchanged original runtime, I/O manager, I/O-driver ABI, and IEC mapping. Keep that compatibility target separate from physical fidelity. Each profile states exact descriptor identity, version, digest, declared fields, chosen virtual process projection, configuration values, supported requests, and unsupported operations. A passing profile test establishes only that exact software profile and test path.

## Alternativen

1. Wait for complete hardware and electrical characterization before any native integration. Rejected because it would block the now-prioritized descriptor/consumer compatibility work.
2. Treat descriptor declarations and consumer predicates as measured hardware defaults. Rejected because they do not describe all register meanings, lower process image, or electrical behavior.
3. Return generic success or zeros for unsupported identity/register operations. Rejected because it can conceal consumer requirements and invent device identity.
4. Replace or imitate the original CODESYS ABI/IEC decision logic in an independent consumer. Rejected because the target is integration through the original runtime path.

## Entscheidung

1. **Keep the original path.** The original runtime, native I/O manager, and original I/O drivers remain in place. The adapter preserves their ABI. It supplies only the explicitly selected virtual profile at the approved lower boundary; it does not replace the IEC application or reproduce PLC decisions in a model.
2. **Bind immutable profiles to exact descriptions.** The pins currently under implementation are:

   The 750-677#16 descriptor labels its exact ParameterId 10 string “Module compare value” / “Desired value”. It declares four channels, each with a status byte, reserved byte, and input WORD, and four output channels with a control byte, reserved byte, and output WORD: 16 input bytes and 16 output bytes total. The selected profile may expose one virtual bidirectional terminal with those declared 16-byte extents. Offsets, packing, and sizes in the virtual rail are explicit profile policy, not asserted hardware or measured runtime layout.
3. **Separate selected model configuration from hardware defaults.** The pinned virtual profiles may choose explicit fixed replies R16=0, R29=0, and R30=0 to satisfy the known FW31 consumer predicates. These values are profile policy only. They are not measured or documented physical register defaults. Profile definitions are versioned and immutable; a changed descriptor, projection, or chosen register value requires a new profile revision and tests.
4. **Preserve consumer predicates and explicit failures.** Table9 and configuration-register calls keep outer dispatch and inner operation status separate. For the statically bound FW31 non-digital validation helper, the known checks are exact: Table9 equals compare group 2, `(R16 & 0x0300)==0`, `R29==0`, and `R30 % 10 == 0`. The listed analog compare groups are directly bound in its descriptor-specific evidence; applying the same helper predicate to 750-677 is a compatibility profile choice that still requires a test of that exact path. These checks do not prove every normal initialization path. A conditional register-28 request is unsupported for the fixed R30=0 profile and must return the explicit unsupported result if it occurs. Unknown registers, unselected profiles, and UID requests fail explicitly and are traceable; no generic zero/success stub or synthesized identity is permitted. The existing call-site evidence does not yet prove whether `get_uid` is reached during normal initialization for every selected profile, so any such request keeps that compatibility result open until its exact caller is qualified.
5. **Define the claim boundary.** A native pass means the bound CODESYS project, descriptor revision/hash, adapter/profile revision, original component path, mappings, configuration, and tested input/output vectors worked together. It does not claim a physical module default, complete process image, byte-for-byte bus layout, electrical output, or hardware equivalence. A descriptor-derived 16/16 virtual process extent is valid as an explicitly named compatibility profile without first resolving whether a physical configuration would use 12 or 16 bytes.
6. **Keep hardware comparison separate.** Physical analog/PWM comparison is a later milestone requiring the correct actual module/revision, separate authorization, and its own bounded and safe plan. Digital DI8/DO8 evidence does not transfer to analog/PWM hardware.

## Risiken

A compatibility profile can satisfy consumer predicates while differing from an actual module. A descriptor field size can be accepted by CODESYS without proving its lower physical packing. Unsupported UID or conditional register calls may block some native initialization path. A native integration pass may therefore be useful and real while remaining narrower than hardware qualification. Profile versioning and evidence must prevent those claims from collapsing.

## Verifikation

For every profile, require exact descriptor hash/version checks, deterministic project build and read-only reopen, exact CODESYS module order/count and mappings, explicit process extents, and a profile-specific test of all supported normal calls and consumer predicates. Negative tests must show unsupported profile/register/UID operations return errors without changing the selected profile or requested output payload and without manufacturing identity. The documented model fault latch and fail-closed effective-output transition may change on an invalid operation. Native runtime trials use only the owner-authorized target and preserve the original runtime/manager/driver path; they require source/provider/configuration binding, closed model permit where applicable, fresh STOP/rollback checks, and no physical output unless a separate plan allows it.

Report separate statuses for CODESYS build/reopen, own-provider tests, original-consumer/runtime integration, physical module comparison, and electrical behavior. Do not upgrade one status from another. Hardware comparison remains **NOT_RUN** until separately planned and authorized.
