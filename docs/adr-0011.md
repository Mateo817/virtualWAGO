# ADR-0011: Opt-in PWM asynchronous-service exploration

## Problem and current state

The native PWM project reaches RUN, but the strict adapter faults on unsupported
GET_UID and asynchronous service calls. Two explicitly synthetic UID replies
reached async-open; open/close exploration next exposed scalar register reads.
This blocks observation of later consumer requests and cyclic output frames.

## Target and decision

Provide a compile-time `VIRTUALWAGO_PWM_ASYNC_EXPLORATION` option for the existing
PWM677 profile only. It requires tracing, returns the previously explored
synthetic UID 750677, manages a bounded pool of own opaque channel tokens and
implements only the observed services whose argument/result ABI is established
from exact FW31 code and authentic headers. A rejected UID query for another
slot retains inner `-1` and leaves its output
untouched, but does not latch a global model fault in this opt-in PWM mode.
Normal builds retain unsupported UID and async behavior. No vendor headers or
binaries enter this repository.

Channel state belongs to the existing adapter lifecycle and mutex. Reset,
Init/Exit and device close invalidate channels. Tokens are not reused within a
process; a token is never a pointer to provider memory or derived from UID.
Device close explicitly cancels pending synthetic reads and invalidates their
tokens; this is own teardown policy, not a claim about vendor cancellation.
All writes through consumer pointers are bounded by the established ABI.
Registers and completion timing in this exploratory mode are explicitly own
synthetic policy, not physical defaults or vendor timing. The own zero bank
accepts slot 1 and all 8-bit channel/register indices; only
channel 0/register 29 was observed natively. A matching poll completes immediately.
This broader bank is an experimental policy, not a verified module register map.
Unknown operations remain unsupported and visible; there is no universal success fallback.

Requested outputs may be observed, but the PWM exploration mode refuses opening
the effective-output permit. Models do not implement IEC application decisions.
Runtime RUN, successful service replies, module readiness, cyclic frame
acceptance and physical equivalence remain separate evidence levels.

## Alternatives

Continue deriving every hardware detail before running: preserves fidelity but
prevents the owner-requested incremental discovery. Return success to every
operation: rejected because pointer extents, handles and later results would be
uncontrolled. Disable the checker fault gate globally: rejected because it
would hide unrelated data-path failures. Keep all exploration as unversioned
patches: rejected for this next step because the owner requests a usable,
testable bounded prototype.

## Risks and verification

Synthetic values may send the original module into a branch unlike real hardware.
A matched process frame is not proof that its module FB is healthy. Live tests
must bind exact artifacts and original runtime, keep outputs closed, preserve
unexpected calls and restore original STOP/files after each bounded run.
Own tests cover opt-in isolation, buffer bounds, pool exhaustion, token uniqueness,
stale handles and lifecycle invalidation. Default profiles receive regression
checks. Record actual native calls and patterns separately from static ABI facts.
No physical PWM or real async bus communication is claimed.
