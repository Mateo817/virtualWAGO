## Create fields and the literal pool

The six Root362 bodies contain 109 source words: create 61, snapshot 19, flip 16, and three leaves with 5/5/3. The create function’s last instruction is at ELF `0x126f8`; its 244-byte body ends at `0x126fc`. The next word at `0x126fc` is a separate nonbody NOP (`0xe320f000`). The following eight bytes are literal words `0` at `0x12700` and `1` at `0x12704`; the retained 12-byte read confirms this exact boundary and content.

Create loads the 64-bit literal at `0x12700` using the PC-relative VFP load at `0x12634`, stores word 2 at current `r4+0x20` at `0x12640`, and stores literal low/high words 0 and 1 at current `r4+0x18/+0x1c` with `VSTR.64` at `0x12644`. If current `r4` still denotes the allocation result, these explicit stores establish `I18=0`, `I1c=1`, and `I20=2`. The remaining decoded r4-relative word stores are at `+0x2c`, `+0x30`, `+0x28`, and `+0x34`; none targets `+0x24`. The function makes opaque calls after assigning `r4` and before/among these stores, so the object-identity and no-intervening-memory-effect premises remain open. The absence of a body store at `r4+0x24` does not prove the byte’s initial or final value and does not prove the opaque allocation returned zeroed memory. `create-store-inventory.tsv` lists the decoded stores and literal read.

## Leaves and mutators

The exact leaf instructions test `r0` for zero and conditionally load the selected word only on the nonzero path. `get_read` uses the current word at `P+0x18`, forms `P+4*I18`, then reads `+0x2c`; `get_write` uses `P+0x1c`; `size` reads `P+0x28`. Their local address calculations wrap at 32 bits and contain no bound check. The stipulated `P=0x3000,I18=7` fixture computes `0x3048` and stops at an unmapped synthetic read. This is not a native fault test or a universal invalid-index result.

For nonnull `flip`, the raw source sequence at `0x127f8/0x127fc/0x12800` is VLD1.32 of one d-register, VREV64.32, then VST1.32 to the same current address `P+0x1c`. The 64-bit value is two 32-bit lanes `(I1c,I20)` in memory order; VREV64.32 reverses those lanes, so the local store exchanges `I1c` and `I20`. The following byte store sets `P+0x24` to 1. For nonnull `snapshot`, a current byte load and compare at `0x127a0/0x127a4` gate the swap. A zero byte skips the three index/flag stores. Any nonzero byte, including 128, loads current `I20` and `I18`, writes byte 0 to `P+0x24`, then writes those words to `P+0x18` and `P+0x20`, exchanging `I18` and `I20`. The six permutations and three numeric byte values are all present in WP369’s 36 transform cases, and the recorded outputs match these formulas.

The null paths return 1 without reaching either direct call; the nonnull paths call raw targets `0x7650` (acquire boundary) and `0x7a70` (unlock boundary). Branch and BL targets were independently recomputed from raw A32 branch words. `r4` contains current `P` at acquire return and the next source operations dereference it, so the model’s `r4=P` premise is required. At unlock return, the source next sets `r0=0` and pops saved `r4`/PC; `r4` preservation by unlock is not required. Normal continuation still requires the opaque calls to return with framed SP and saved-frame memory usable.

## Material model boundaries

WP369’s `trace-cases.json` keeps per-case executed PC lists, final index/byte values, and opaque-boundary dictionaries. It does not retain per-instruction register snapshots, NZCV values, individual memory events, or stack read/write events. Its validator checks each exact raw word and uses PC-specific source semantics, including manual NEON lane swap; it is a purpose-built source stepper, not a general ARM decoder. This review checked all saved PC paths, raw source words, create/leaf formulas, and the 36 finite transform results, but cannot inspect per-step events that are absent from the artifact.

The fixture seeds object bytes before the acquire call and leaves its memory unchanged while modeling the opaque boundary. To associate the fixture’s entry tuple with the later mutator loads, either those relevant bytes must be stipulated unchanged by acquire or the tuple must be defined as the current post-acquire state. Similarly, the source-local flip/snapshot stores are visible before the unlock BL, but WP369 collects `post_indices` after modeling unlock return while leaving object memory untouched. A whole-function returned-memory claim therefore also requires unlock to preserve those bytes; WP369 states the frame/SP condition but does not separately model or stipulate unlock memory effects. The safe local result is the source’s pre-unlock store sequence under readable/writable current memory. `opaque-premises.tsv` separates these premises from the verified source effects.

No source fact in this audit establishes allocation zero-fill, constructor reachability, callback binding, common runtime object identity, API/descriptor semantics, synchronization or atomicity. No upstream files were changed. `review-matrix.tsv` records the independent findings and limits.
