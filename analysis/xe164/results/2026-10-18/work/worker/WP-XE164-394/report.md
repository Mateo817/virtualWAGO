# WP-XE164-394 — independent review of WP-XE164-390

Independent source review. **VERIFIZIERT**: all 224 selected instruction words and three literals map to the exact raw FW31 ELF bytes; the 12 PLT/GOT relocation equations, Init’s numeric `(r0=1,r1=0x74)` call vector and publication order, Open’s unsigned index gate, S0/S1 reload, field offsets, I3 interval arithmetic, and the selected backend callsite. **PASS**: this review’s read-only validator and WP390’s source/data assertions. WP390’s default validator is not strictly filesystem-read-only because importing `build_source` can create `__pycache__/build_source.*.pyc`; its listed research artifacts remained hash-stable. Runtime binding, actual allocator behavior/extent, common object identity, caller reachability, API/ABI, and hardware/runtime effects remain **OFFEN**. Target/VM/network execution is **NOT_RUN**.

The pinned ELF is `libpackbus.so.1.0.1`, SHA-256 `3b7b7ca4fa14e5994552040a7b40b1cfbbf43e0649a4ad9277ece421fd4bc5d6`. I parsed its ELF32 program headers and resolved each selected VA through a unique file-backed `PT_LOAD`; all 224 words and three literal words match the copied table and raw bytes. The executable body spans contain 165 Init words (`0xdd6c..0xdffc`) and 23 Open words (`0xe008..0xe060`). The table’s first-column labels show 168 rows named `SSC_Init` and 26 named `SSC_Open` because each label also includes its three-word local PLT stub; ten other PLTs add 30 words. Thus the 224-word inventory is consistent with 188 body words plus 36 PLT words.

I independently parsed the ELF `SHT_REL` and symbol/string tables, decoded all twelve retained three-word PLT stubs, and matched each computed GOT address to its raw `R_ARM_JUMP_SLOT` name. The Init/Open global-cell literals resolve to `G=0x443f4`; the Init configuration literal resolves to `0x1e6a0`. This validates static source/link metadata, not which implementation the runtime loader will call.

Init writes `r1=0x74`, then `r0=1`, and calls the calloc-named PLT at `0xdd7c`. It computes G from the literal, stores the current call return word through `[r4]` at `0xdd8c`, then reaches the first create-lock call at `0xdd98`. For the first lock vector, the source directly adds `0x2c` to the same current `r0` that it just published; the source does not reload G between those instructions. After that call, it loads `[r4]` and adds `0x44` for the second lock vector on the zero-return branch. So the statement “publication before locks” is exact. Continuation across later opaque calls still depends on `r4` retaining the G-cell address, the active stack frame and `[sp+4]` value remaining usable, and any global/instance words subsequently loaded having the expected current contents. These are source execution premises, not a derived ABI or callback-preservation guarantee.

Open compares entry `r0` with 3 using unsigned `HI`; indices 0 through 3 proceed, while greater indices take the local zero-result route. It loads `S0=[r5]` and passes `S0+0x2c` to the acquire PLT. After normal continuation it loads `S1=[r5]` again, then computes `Q=S1+8*I`. The source checks `[Q+0x60]`; if that word is zero, it stores I at `[Q+0x5c]`, stores S1 at `[Q+0x60]`, and forms result `Q+0x5c`. If the word is nonzero, it forms result zero. After unlock, the source copies its current `r4` to `r0` and pops the saved frame. The equations require `r5` still to designate `G=0x443f4`, `r4` still to hold I during the selected path, normal call returns, a valid active SP/frame, and current global/slot memory readable or writable as accessed. After unlock, `r4` must still contain the selected result and the pop frame must be intact. WP390’s phrase “required GP/frame values” covers these requirements generally; this review makes the specific live values explicit. No ABI is inferred.

The source has no S0/S1 null comparison before using them. Its two comparisons are the unsigned index check and the selected slot word `[Q+0x60]`. Thus a claim that Open locally rejects a null S pointer would be wrong; readable global and S-derived addresses are fixture/runtime premises. S0 and S1 are separately loaded values. Equality is not needed for the arithmetic on S1 itself, but is required if one claims the acquire argument and subsequent table accesses refer to the same object.

For I=3 the access interval is `[S1+0x74,S1+0x7c)`: the empty-slot write occupies `[S1+0x74,S1+0x78)` and the slot read/write occupies `[S1+0x78,S1+0x7c)`. Init’s raw vector is `(1,0x74)`. Under the conventional calloc interpretation this is a request for a `0x74`-byte extent, so the I3 span is numerically beyond `[S,S+0x74)` **if** Open’s S1 equals that Init return value S. That is a conditional offset comparison, not an actual memory-bug finding: actual allocation behavior/extent, S1 identity, and call reachability are not established here.

The pinned Root310 backend caller has a raw `MOV r0,#0` at ELF `0x10910` immediately before its `BL` to the SSC_Open PLT at `0x10918`; this callsite supplies I=0 on its normal source continuation. It also has a BL to SSC_Init at `0x108e0`. The next source instructions derive/load a separate backend global cell and later test that loaded word; they do not immediately compare Init’s returned `r0`. This remains one static caller observation, not proof of runtime reachability or successful initialization.

WP390’s validator reconstructs tables in memory and its assertions pass, but it imports `build_source` under the default Python bytecode behavior. On my default invocation, that created `__pycache__/build_source.cpython-*.pyc`, so a strict no-filesystem-write claim is false even though no research output changed. I removed that generated cache to restore the original package state; all paths in WP390’s manifest passed both before and after. Setting `PYTHONDONTWRITEBYTECODE=1` avoids this incidental cache write. The independent checker in this package is read-only and does not execute target code or alter upstream packages.
