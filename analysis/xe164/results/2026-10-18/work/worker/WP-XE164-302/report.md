## Stepper defect at the status lane

WP300's `run_source_stepper` models Ghidra `0x55e60` as `r11=(r8<<2)` and `0x55e64` as a bucket load. The raw source says otherwise: `0x55e60` is `LDR r3,[r2,r11]`; `0x55e64` is `CMP r3,#1`; and `0x55e68` is `BLS 0x55e54`. The `r11=(r8<<2)` instruction belongs to the separate later-probe lane at `0x55e5c`, which the positive A/B trace does not visit. The validator also omits the compare's flag update, so its BLS consumes stale C/Z flags from the equality-result comparison.

For both fixed fixtures, current `r11` is already zero from the selected index, and the status word is 7. The actual source performs `CMP 7,#1`, giving C=1,Z=0, then does not take BLS. The stale flags after equality result `1` versus zero are also C=1,Z=0. Therefore this error does not alter the A/B PC sequence or returned value. It does mean the stepper's intermediate state at these PCs is not a faithful instruction-level replay, and it would not correctly model the local `status<=1` control boundary if that state were presented. In an isolated lane check, actual `CMP 1,#1` or `CMP 0,#1` takes BLS to the zero return; the stepper's stale flags would leave BLS untaken. Those are local instruction controls, not claims that the same bucket can change between the first-hit and status reads in the immutable A/B fixtures.

The independent raw word check is recorded in `status-lane-check.tsv`; the exact source/body/stepper pins are in `source-pins.tsv`. WP300's `trace.tsv` labels the status load and comparison at the correct PCs, but its `validate.py` implements those two effects one instruction late.

## Other review findings and confirmed route

WP300's `model_positive` makes an immediate copy of `mem`, then compares it to the unchanged dictionary; it also asserts `(sp-40)+40==sp`. These do not simulate writes or stack effects. They are tautologies and should not be counted as validation evidence for immutable memory or frame balance. The separate selected-PC stepper has a meaningful final-SP and saved-register restoration check. More directly, the inspected selected source path contains no ordinary data store, and the two callback leaves contain no store, so the bounded no-non-stack-write conclusion is supported by the source instructions rather than the snapshot equation.

The rest of the fixture arithmetic and domains check out. The lookup PC labels are Ghidra VAs, each corresponding ELF VA is exactly `Ghidra-0x10000`, while the synthetic fixture pointers are just numeric model addresses. The hash callback receives the query pointer and loads 7. The lookup chooses multiplier 7, forms 77, and calls `FUN_000cac64` with `r0=77,r1=1`. That helper saves `{r0,r1,lr}` in 12 bytes and calls the nested body. At nested `r1=1`, `SUBS r2,r1,#1` yields zero and sets Z; raw `BXEQ LR` returns the unchanged current `r0=77` immediately. The outer helper restores saved `r0` into `r1=77` and divisor into `r2=1`, computes `r3=77`, then `r1=0`. This route does not enter the nested computed-PC/divide loop and proves no general division contract.

For the stated first-bucket fixture, index 0 reads cached hash 7 and the stipulated equality callback is passed stored-key/query pointers. The six pinned equality words read 7 and 7, subtract to zero, compute `CLZ(0)=32`, shift right five, and return 1. The lookup then loads the same bucket word 7 in its status lane, compares against 1, and loads `values[0]` because BLS is false. Fixture A returns `0x25000400`; B returns `0x5500c400`. The source prologue saves ten registers (40 bytes); the nested helper uses a 12-byte frame and restores it before returning. These are conditional source/synthetic facts assuming the mapped words, callback token mapping, nonaliasing, no external interference, and normal returns through the visible LR chain.
