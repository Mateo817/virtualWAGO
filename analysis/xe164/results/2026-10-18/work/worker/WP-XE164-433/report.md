# WP-XE164-433 — bounded WP430 boot call to the frozen WP370 orchestrator

**VERIFIZIERT, source-bound join:** WP430's exact FW31 `SCPU_boot_slave` caller at ELF `0xa744..0xa774` directly calls `0x9a78`, which is the same-image orchestrator already inventoried in frozen WP370. WP370 proves a noncontiguous orchestrator body at `[0x9a78,0x9e78)` and `[0x9f24,0xa470)` (595 words); the intervening 172 bytes are not body words. This package reuses and verifies that inventory instead of treating the enclosing linear span as code. WP430's `0x9a78` callee was unexpanded in WP430; WP370 independently provides the existing source body and reader source. No upstream package was changed.

At the selected boot callsite, the words set `r0=SP+0x20`, load `r1=[SP+0x14]`, set r3=1, compute current r4 as `PC+8+word[0xa8c8] = 0x40028`, store 1 at `[r4]`, and branch-link to `0x9a78`. The orchestrator entry's `STRD r0,r1,[sp,#0x14]` saves those numeric incoming values in its own frame at offsets +0x14/+0x18. It then initializes local words at SP+0x38 and SP+0x3c and invokes the already inventoried reader at `0x9ae0` with numeric `(r0=0, r1=SP+0x38, r2=SP+0x3c)`. These are observed register/address equations, not prototypes or structure fields.

The reader's code and static row data share the pinned libpackbus image. WP370 records 11 static loader rows and exact file identities: FW31 `XE164L1.bin`, `XE164L2.bin`, and `XE164L3.bin` match the retained WP004 files byte-for-byte. Its configured candidate summary is a static derivation (prefix `00 00 40 d6`, L3 bytes, XOR `83`, with candidate selected rows 7/8/9 labeled a hypothesis). The checker independently reconstructs the listed prefix + exact L3 file + XOR bytes and matches WP370’s composite digest. This supports source-payload identity for those local files, not evidence that the boot call selected or transferred that candidate. The boot helper's surrounding code also uses local serial-related call vectors; none is executed here.

A bounded failure edge is directly visible: if the reader's first return at `0x9ae0` is `0xffffffff`, `CMN r0,#1` and `BEQ 0xa208` select a local epilogue that sets helper r0=0 and returns. Back in the boot caller, `CMN r0,#1` sees zero, so `MOVNE r3,#2; STRNE r3,[r4]` conditionally changes current G from 1 to 2. This is a conditional numeric source path only. It does not attach “success” or “failure” meanings to those words, establish that the reader returns `-1`, or summarize the rest of the orchestrator's paths.

The 638-word contiguous inventory initially drafted in this package has been removed: it crossed the orchestrator's 172-byte non-code gap and included WP430's separate boot body, so it could not be presented as a helper body. The final validator checks the canonical noncontiguous WP370 inventory and exact caller/helper words. The authorized REA query did not return data because no app was open; I did not switch targets. No native execution, serial access, firmware transfer, VM, network, or device operation occurred.
