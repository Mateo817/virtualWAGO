# WP-XE164-341 — independent audit of WP330 vararg marshalling source claims

**VERIFIZIERT (statisch, hashgebunden):** I independently checked the raw libdal A32 words underlying WP330’s selected wrapper, common marshalling body, helper, dispatch stubs, and `ffi_call` site. The raw input is `libdal.so.1.0.1`, SHA-256 `c163ac57805409921ce783f9c4f17f52891864be333c3df4945a128d253994f5`. The frozen WP330 manifest SHA-256 is `cfb85ca50aee59303434f481cfdc915ad4126326a2c8fb0370f23f35b074503c`; its manifest and all listed artifacts still verify. I did not invoke or modify WP330’s builder or validator.

The 168 source-word inventory agrees byte-for-byte with the pinned input, and I independently decoded all 30 inline A32 `B` stubs from their raw words. Both `ADDLS pc,pc,tag,LSL #2` dispatches have the expected unsigned `tag <= 14` guard. The argument dispatch maps tags 0–14 to `0x2894, 0x2880, 0x2978, 0x2958, 0x2950, 0x2918, 0x2918, 0x2900, 0x2900, 0x2880, 0x2880, 0x2930, 0x2930, 0x2950, 0x2880`. The return dispatch maps them to `0x2874, 0x299c, 0x29d8, 0x29cc, 0x2870, 0x29c0, 0x29c0, 0x29a8, 0x29a8, 0x299c, 0x299c, 0x29b4, 0x29b4, 0x2870, 0x299c`. These numeric mappings confirm WP330’s dispatch summary.

At the 0x70 wrapper entry, let SP be `S`. Its push stores entry `r1/r2/r3` in `[S-12,S)`, saves LR at `S-16`, and reserves eight local bytes `[S-24,S-16)`. Immediately before its BL to `0x2784`, `r0` still has entry `r0`, `r1` has the saved entry `r1`, and `r2=S-8` points to the saved entry `r2/r3` words. The local store at `[S-20]` writes that pointer. Its epilogue returns SP to `S` and restores LR. These facts match WP330; the wrapper’s explicit saved-word range covers only two input words, so any later reads through the advancing source pointer require additional readable-memory premises.

The common body sets `r5/r6/r4` from entry `r0/r1/r2` before its opaque calls. Its source then tests the numeric result of the call at `0x2180`; zero takes the `-1` return path, nonzero continues. It calls the name helper at `0x20b0`, assigns that helper’s result to current `r5`, and passes `[r5+0x38]` to the helper at `0x2194`; a zero result takes the `-1` path. A null name-helper result takes the separate `1` return path. The source establishes these numeric branches, but the callee bodies were not expanded here; labels such as “global gate” remain shorthand for the observed call-and-test sequence, not a proven semantic contract.

The `ffi_call` call vector is sourced directly by the four instructions at `0x28a0..0x28ac`: `r1=[current r5+4]`, `r0=current r5+8`, `r2=current r8`, then BL to `0x1504`. For a nonzero argument count, `r3` is set at `0x2814` to the stack pointer after the second aligned allocation; `r12` receives the same vector base, and each supported argument handler stores its per-value pointer through `[r12]`. The common loop advances `r12`, while `r3` is not modified by the argument handlers. For zero arguments, `r3` still contains the zero count loaded at `0x27cc`; the zero branch reaches the call without another `r3` write, so the source passes `r3=0`. `r8` is set to the current SP before either call path. The exact local call vector is therefore confirmed, including the zero-argument case.

Mapping these register values back across the prior helper calls is conditional: the source uses `r5`, `r6`, and `r4` after opaque calls, but this bounded audit does not establish the callees’ register or memory effects and does not import an ABI preservation rule. Likewise, the final `ffi_call` JUMP_SLOT names `ffi_call@LIBFFI_BASE_8.0` at ELF `0x1409c`, but the actual runtime binding and call effects are not established.

**Material qualification:** unsupported argument tags do not fail fast in this source. Tags 4, 13, and values above 14 set `r7=0xffffffff` and rejoin the common loop advance; the source proceeds toward `ffi_call` once the loop ends. These cases do not execute a source-value load through `[r4]` or store a new staging pointer through `[r12]`, although the vector cursor advances. Thus the associated staging slot is not initialized by this path, and the input cursor does not advance for that argument. This is a source-level memory/register fact, not a claim about the value later observed by `ffi_call`. Whether the `r7` marker survives the opaque call or determines the eventual returned value is **OFFEN**; no ABI-preservation conclusion is drawn. Tag 0 also advances without a staging-slot store, but does not set the error marker.

WP330’s statements about the selected dispatch targets, the numeric error assignment, and continued source flow to the `ffi_call` site are supported. Its call-vector statement is precise when read as values at the call instruction. Any interpretation of those values as preserved entry arguments, global/device semantics, supported application-level argument types, runtime output, or an ABI contract remains conditional or **OFFEN**, as WP330 already scopes it. No amendment to WP330 is made.
