# WP-XE164-339 — independent audit of WP334 table and type metadata

**VERIFIZIERT (statisch, hashgebunden):** I independently parsed the raw libpackbus ELF and its `readelf` program-header and relocation metadata, then compared the resulting bounded table facts with both WP334 derived TSV inventories and retained REA-facing fields. The audited libpackbus is 148,792 bytes, SHA-256 `3b7b7ca4fa14e5994552040a7b40b1cfbbf43e0649a4ad9277ece421fd4bc5d6`. The argument span is 444 bytes and contains 110 argument-type pointers across 28 populated rows; row 28 is the first following all-zero 52-byte sentinel.

The raw getter at ELF `0x0ec88` contains the 12 bytes `04 00 9f e5 00 00 8f e0 1e ff 2f e1`. Its pool word at `0x0ec94` is `0x24b64`, and the observed PC-relative equation is `0xec94 + 0x24b64 = 0x337f8`. The two file-backed `PT_LOAD` mappings directly establish the table file range `[0x237f8,0x23ddc)` and argument-cell range `[0x23ddc,0x23f98)`. The mapped argument span is `[0x33ddc,0x33f98)`. The offset stated in WP334’s report, `[0x25ddc,0x25f98)`, is outside the pinned 148,792-byte file and is incorrect; this is a report prose error, not a raw source or table-inventory defect.

I compared raw row names, `+0x20` words, function-field raw contents, argument counts, argument-pointer raw contents, and relocation kinds/symbols with `row-review.tsv` and WP334’s `record-inventory.tsv`. I independently resolved every argument vector through the row’s fixed pointer field, read each cell from the raw mapped bytes, and matched all 110 zero-addend `R_ARM_ABS32` relocations to the WP334 `argument-type-relocations.tsv`. The two TSV inventories agree with the raw fields, argument ordering, and relocation symbols. The argument type counts are `ffi_type_uint8`: 50, `ffi_type_pointer`: 42, `ffi_type_uint16`: 15, and `ffi_type_uint32`: 3. In particular the three `uint32` argument cells are row 21 (`libpackbus_get_dig_offset`, argument 0), row 22 (`libpackbus_set_dig_offset`, argument 0), and row 24 (`libpackbus_get_terminal_info_32`, argument 0). The pinned WP334 TSV inventories already include all three with exact `LIBFFI_BASE_8.0` versions and matching REA external tokens. Thus WP334’s omission of `ffi_type_uint32` from the argument-types sentence is a prose-only defect; neither derived table nor its type-cell data is missing those entries.

The 28 return relocations independently identify `ffi_type_sint32@LIBFFI_BASE_8.0` in 26 records and `ffi_type_uint32@LIBFFI_BASE_8.0` in two. All 110 argument cells and all 28 return cells are raw zero-addend `R_ARM_ABS32` references to versioned external type symbols. Their WP334 REA values (`0x5816c`, `0x581f0`, `0x58148`, `0x58058`, `0x5808c`) are retained analysis tokens and not runtime pointers. The raw relocation names and those retained tokens agree in both WP334 inventories.

The exact local candidate `libffi.so.8.1.4` is 46,764 bytes, SHA-256 `d162a9b28a30f10bd8baacac3a62b32148563e3b1e4d25c81361211d3172c4f5`. Direct `readelf -Ws` inspection confirms the five referenced symbols are 12-byte `OBJECT`, `GLOBAL`, `DEFAULT` entries, versioned `LIBFFI_BASE_8.0`: `ffi_type_pointer` at `0xa300`, `ffi_type_sint32` at `0xa324`, `ffi_type_uint32` at `0xa330`, `ffi_type_uint16` at `0xa348`, and `ffi_type_uint8` at `0xa360`. This establishes metadata for the pinned local candidate only; it does not establish runtime library selection, binding, or relocation results.
